### 1.3 The two data domains (CRITICAL architectural concept)

The app has **two completely separate data layers** — confusing these is the #1 source of bugs:

1. **Static content data** (read-only, in `public/data/`)
   - Pre-built JSON files generated by the Python pipeline (`scripts/`)
   - Vocab words, grammar rules, questions, narration/voice, roots
   - Served as static files via Cloudflare CDN
   - The worker does NOT touch this — it's just static hosting
   - **Cache headers** set by `functions/data/_middleware.ts` (browser 1 day + CDN 30 days)

2. **User data** (read-write, in D1)
   - Per-user state: accounts, problematic items, progress, test attempts
   - Only the worker touches this, via D1 binding `DB` (declared in `wrangler.toml`)
   - **Auth required** on every `/api/*` endpoint (except `auth/me`, `auth/signup`, `auth/login`, `auth/signup-status`)

## 4. Auth & security model

- **Cookie-based session auth** with self-contained JWT (HS256, signed with `JWT_SECRET` env var)
- **Password hashing:** PBKDF2-SHA256, 100k iterations, 16-byte hex salt
- **Cookie:** `svm_session`, HttpOnly + Secure + SameSite=Lax, 1-year expiry ("stay logged in forever")
- **First user to sign up = admin** (bootstrapping pattern)
- **Public routes:** `/`, `/login`, `/signup` only — everything else requires auth
- **Route gating (two layers):**
  1. Client-side inline script in `Layout.astro` (probes `/api/auth/me`, redirects on definitive no-user)
  2. Server-side `requireUser()` / `requireAdmin()` on every `/api/*` endpoint

See [`docs/AUTH_SECURITY.md`](./AUTH_SECURITY.md) for full details.

### Known auth race (fixed in session 5, pattern to remember)

Any component that depends on auth state must `await loadSession()` in its OWN `onMount` — never trust that another component (e.g. `AuthBar` with `client:idle`) has loaded it. Components with `client:load` run before `client:idle` ones.

```ts
// CORRECT pattern (used in ProblemsView, ProgressTracker, TestList, etc.)
onMount(async () => {
  await loadSession();
  loggedIn = isLoggedIn();
  unsub = onAuthChange((u) => {
    const now = !!u;
    if (now !== loggedIn) { loggedIn = now; if (now) refresh(); }
  });
  await refresh();
});
```

## 6. Content data structure (the #1 source of bugs)

### 6.1 Question shape (`QuestionEntry` in `vocab-data.ts`)

```ts
interface QuestionEntry {
  id: number;
  exam?: string;        // e.g. "CGL Tier-1 2024"
  year?: string;
  satwik_id?: number;
  qtype: 'synonym' | 'antonym' | 'one-word' | 'idiom' | 'homonym' | 'spelling';
  prompt?: string;      // the question instruction
  stem: string;         // ⚠️ SEMANTICS VARY BY QTYPE — see below
  options: string[];    // 4 options
  correctIdx?: number;  // 0-3, real SSC answer (from Satwik)
  expl?: string;        // explanation
  src?: string;         // source file:line
  sent?: string;        // ⚠️ SEMANTICS VARY BY QTYPE — see below
}
```

### 6.2 ⚠️ CRITICAL: `stem` and `sent` semantics vary by qtype

This is the #1 source of MCQ display bugs. The meaning of `stem` and `sent` depends on the question type:

| qtype | `stem` contains | `sent` contains | What to show as the question |
|---|---|---|---|
| synonym (no sentence) | the word to find synonym for | (empty) | `stem` |
| synonym (underlined in sentence) | the underlined word | the full sentence | `sent` + "Underlined word: `stem`" |
| antonym | same as synonym | same as synonym | same as synonym |
| **one-word (OWS)** | **the ANSWER word** (e.g. "Atheist") | **the description** (e.g. "A person who does not believe in God") | **`sent` ONLY** — NEVER show `stem` (it's the answer!) |
| **idiom (with context)** | the idiom phrase | the sentence containing it | `sent` |
| **idiom (no context)** | the idiom phrase | equals `stem` (just the phrase) | **"What does this idiom mean?"** prompt — NEVER show the idiom (it's also an option) |
| **homonym** | the answer word | the fill-in-the-blank sentence | `sent` + collapsible "Confused pair" heading (the options) |
| spelling | the correctly-spelt word | the sentence (if any) | `sent` if available, else generic prompt |

**Rule of thumb:** for OWS, idioms, and homonyms, the `stem` field often contains the ANSWER, not the question. Always check `sent` first. See `MCQCard.svelte` for the full implementation of this logic (rewritten in session 8).

### 6.3 Per-letter lazy loading (FAST path)

- `public/data/wq/<letter>.json` — per-letter word→questions (~230KB each, cached)
- `public/data/enriched/enriched_<letter>.json` — per-letter word details (~500KB each)
- `public/data/grammar/qs/gr-<no>.json` — per-rule grammar questions (lazy-loaded)
- `public/data/top_words.json` — dashboard summary (6.8KB vs 2.2MB `words.json`)

**NEVER** fetch `questions.json` (2.45MB) or `words.json` (2.2MB) on a per-interaction basis. Use the per-letter files. This was the session 4 speed fix.

### 6.4 Cache headers

`functions/data/_middleware.ts` sets long cache headers on all `/data/*.json`:
- Browser: `max-age=86400` (1 day) + `stale-while-revalidate=604800` (7 days)
- CDN: 30 days

## 7. Mock test system (session 7)

Fully implemented. See [`docs/FUTURE_ROADMAP.md`](./FUTURE_ROADMAP.md) (all features marked ✅ IMPLEMENTED).

### Key files
- `functions/_lib/test-engine.ts` — pool builder, generator, scorer, auto-problematic
- `functions/api/test/{generate,[id],submit,list,configs/index}.ts` — 5 endpoints
- `src/lib/test-api.ts` — client API + 4 presets + 8 categories
- `src/components/{TestList,TestRunner,TestResults,TestCard,CustomTestBuilder}.svelte`
- `src/pages/{tests,test,test-results,tests/custom}.astro`

### Security model
- Correct answers looked up **server-side** from `/data/*.json` — client only sends selected option index (no cheating)
- Per-user isolation (can't access other users' tests/configs)
- All endpoints require auth

### Test flow
1. User marks words/rules as "read" via ProgressTracker on any module page → updates `progress.completed`
2. User visits `/tests` → picks a preset or saved config, or builds a custom one
3. `POST /api/test/generate` → server builds question pool from `progress.completed`, creates `test_attempts` row, returns question refs
4. User takes test at `/test?id=X` — `TestRunner` fetches question payloads via `/data/*.json`, shows one at a time, timer counts down
5. `POST /api/test/submit` → server scores (looks up correct answers server-side), stores `test_results`, auto-adds wrong answers to `problematic`
6. User sees results at `/test-results?id=X` — score, per-category breakdown, per-question review with explanations

## 8. Common pitfalls (lessons from 8 sessions)

### 8.1 Astro static build can't pre-render runtime-created IDs
The mock test `attempt_id` is created at runtime (in D1). Astro static build can't pre-render `/test/[id]` for IDs that don't exist at build time. **Solution:** use query params instead — `/test?id=X` reads the ID from `Astro.url.searchParams`.

### 8.2 `client:load` vs `client:idle` vs `client:visible`
- `client:load` — hydrate immediately (blocks render). Use for critical interactive components.
- `client:idle` — hydrate when browser is idle. Use for below-the-fold components (AuthBar, ProgressTracker).
- `client:visible` — hydrate when scrolled into view. Use for far-below-the-fold components.

The auth race bug (session 5) was caused by `client:load` components depending on a `client:idle` component having loaded the session first.

### 8.3 Svelte 5 `$bindable()` must be inside `$props()`
```ts
// WRONG
let _x = $bindable(x);

// RIGHT
let { x = $bindable<number>(0) }: { x?: number } = $props();
```

### 8.4 Wrangler bundler is stricter than tsc
`tsc --noEmit` may pass even when the wrangler Functions bundler fails. Always run `npm run build` (which triggers wrangler) before declaring done. Session 7's `validateTestConfig` vs `validateConfig` mismatch was caught this way.

### 8.5 Never commit secrets
- `.gitignore` blocks `.env`, `jwt_secret.txt`
- After pushing with a PAT, immediately `git remote set-url origin` to remove it
- API keys in `scripts/ai_helper.py` read from env vars (not hardcoded)

### 8.6 Satwik data has known issues
See `SATWIK_DATA_ISSUES.md`. The parser already fixes:
- 173 SA questions with empty `main` (recovered 156 via regex on `expl`)
- 361 idiom questions where `main` was the underlined segment (replaced with `opts[ans]`)
- 74 spelling questions with empty `main` (skipped)
- 20 homonym questions with empty `main` (used `opts[ans]`)

### 8.7 The deployed site is the source of truth
The user tests on https://sscpyqs.pages.dev. If it works there, it's done. If not, it's not done — even if it works locally.

## 9. How to extend the project

### Add a new vocab module page
1. Create `src/pages/<name>.astro` (copy `stems.astro` as template)
2. Add to `navItems` in `src/components/Nav.svelte`
3. Add a module card to `Dashboard.svelte` `modules` array
4. If it has a progress tracker, add the `page_type` to the progress API

### Add a new API endpoint
1. Create `functions/api/<path>/<name>.ts`
2. Use `getUser()` + `requireUser()` / `requireAdmin()` for auth
3. Use `ctx.env.DB.prepare(...).bind(...)` for SQL (parameterized — no injection)
4. Return via `json(data, status)` helper from `_lib/auth.ts`

### Add a new mock test category
1. Add to `VALID_CATEGORIES` in `functions/_lib/test-engine.ts`
2. Add a pool builder function (like `buildVocabPool` / `buildGrammarPool`)
3. Add to `CATEGORIES` in `src/lib/test-api.ts`
4. Add to `CATEGORY_TO_ITEM_TYPE` mapping for auto-problematic

### Regenerate content data
See `docs/DATA_PIPELINE.md`. The Python pipeline in `scripts/` handles:
- `parse_ssc.py` — SSC .txt → questions + words
- `enrich_vocab.py` — NLTK WordNet enrichment
- `build_word_questions.py` — word → question IDs mapping
- `split_enriched.py` — split by letter for lazy loading
- `split_word_questions.py` — per-letter wq/ files (FAST path)
- Grammar pipeline (extract_pdfs, parse_grammar_txt, structure_pdfs, merge_rules, answer_explain, etc.)
